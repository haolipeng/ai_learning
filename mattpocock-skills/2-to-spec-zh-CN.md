## 它做什么

`to-spec` 会把当前对话和你对代码库的理解整理成一份规格说明（你可能也把这类文档叫作 PRD），然后发布到你的 issue tracker。

它**不会**再次访谈你。等你使用它时，共识应该已经形成了；`to-spec` 做的是综合整理已知信息，而不是重新问一轮问题。

## 什么时候用它

你需要手动输入 `/to-spec` 来调用它，agent 不会自行选择这个 skill。

当一次改动已经讨论清楚，领域语言也已经定下来，而你希望在写代码之前把这份共识记录下来时，就使用它。

如果计划和领域语言还没有形成共识，先使用 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 做追问。

如果要把完成的规格说明拆成 tickets，则使用 [to-tickets](https://aihero.dev/skills-to-tickets)。

## 前置条件

`to-spec` 会发布到你的 issue tracker（用于管理任务和问题的系统），所以这个仓库必须先通过 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 配置好 issue tracker 和 triage labels（用于标记任务状态和分类的标签）。它会自己加上 `ready-for-agent` 标签，不需要再单独跑一遍 triage（任务分流）。

## 规格说明包含什么

生成的规格说明会把这次改动讲清楚，并为后续实现留下可检查的依据。它通常包括：

- **问题陈述**：结合项目语境说明当前缺什么、哪里不对，以及为什么值得解决。
- **解决方案**：先描述修复方向和整体方案，不急着进入实现细节。
- **用户故事**：列出用户应该能做什么，每一项都要能单独判断是否完成。
- **实现决策**：记录对话中已经达成共识的技术决策，避免后面反复争论。
- **测试决策**：说明功能会在哪些测试边界上被验证，以及怎样判断已经完成。
- **范围之外**：明确这次改动不处理哪些内容，避免 ticket 范围失控。
- **补充说明**：记录其他需要带到后续流程中的信息。

以“用户登录”为例，一份规格说明可能会这样组织：

| 内容 | 示例 |
| --- | --- |
| 问题陈述 | 用户无法稳定登录，导致已有账号无法进入产品。 |
| 解决方案 | 增加登录流程，包括表单、校验、错误提示和登录后的跳转。 |
| 用户故事 | 作为已注册用户，我可以输入账号凭证登录，以便继续使用自己的账号。 |
| 实现决策 | 复用现有 session 机制，不新增独立 token 系统。 |
| 测试决策 | 在登录表单和认证接口两个边界验证成功、失败和异常状态；用户成功登录并跳转到目标页面即视为完成。 |
| 范围之外 | 本次不处理第三方登录、忘记凭证和账号注册。 |
| 补充说明 | 错误提示沿用现有表单规范，并避免暴露账号是否存在。 |

## 测试边界与 deep module

在写规格说明之前，`to-spec` 会先和你确认：这个功能应该从哪里进行测试，以及怎样判断它已经完成。

它会优先使用现有的测试入口，而不是为了这次改动专门增加新的入口。理想情况下，整个功能只需要通过一个稳定的接口来验证。

这也是 deep module 的意义：把复杂的实现细节封装在一个小而稳定的接口后面。只要这个接口保持稳定，底层代码即使发生变化，测试也不需要跟着重写。

打个比方，一个好的模块就像微波炉，你只需要按几个按钮就能加热食物，内部的电磁波原理完全不用管。这种叫做「深」模块 deep module，**接口简单，实现复杂**。

![image-20260724145112470](./picture/image-20260724145112470.png)

这对 AI 智能体参与的开发尤其重要。测试应该依赖稳定的接口，而不是依赖容易变化的内部实现。

例如，登录功能可以通过认证接口验证，而不必分别测试接口内部的凭证校验、会话创建和错误处理实现。



## 它运行良好的表现

- 它开始撰写规格说明，而不是重新问你一轮问题。
- 它会在写之前和你确认测试边界，并且提出尽可能少的边界。
- 规格说明会使用你项目里的领域语言，而不是泛泛的模板话。



## 它放在什么位置

`to-spec` 是主构建链路中的一步：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

在计划和领域语言都已经明确之后、把工作拆成可实现的 tickets 之前使用它。

它最接近的两个 skill 是 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 和 [to-tickets](https://aihero.dev/skills-to-tickets)：前者会把上下文打磨清楚，让规格说明更加精确；后者会把规格说明拆成一组 tickets，交给 [implement](https://aihero.dev/skills-implement) 去构建。

当你不确定该用哪个 skill 或哪条流程时，[ask-matt](https://aihero.dev/skills-ask-matt) 会帮你选择。
